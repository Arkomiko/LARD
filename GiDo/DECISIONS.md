Новые записи добавляются в конец. Если решение потом пересматривается, старая

Если журнал расходится с техническим заданием, прав журнал: в нём записано то,

## Ждут решения автора

Вопросы, на которые нужен ответ автора. Когда ответ получен, вопрос
переезжает ниже как обычная запись.

1. **Паспорт мода и правило «все тексты — в GiDo/».** ТЗ требует, чтобы в каждом
   моде лежали `MOD_INFO.txt` и папка `licenses/`. Значит, учебные моды в `mods/`
   нарушат правило 9 («`.md` и `.txt` — только в `GiDo/`»).
   *Предложение:* записать моды в исключения правила 9 — без паспорта мод
   не загрузится вовсе.
2. **«Рабочая область» и «рабочее пространство».** В ТЗ есть два разных понятия:
   рабочая область (раскладка окон и панелей, пресет) и рабочее пространство
   (`.mpln`, набор проектов). По-английски оба — *Workspace*, в коде их легко
   перепутать.
   *Предложение:* в коде раскладку окон называть `Layout`, набор проектов —
   `Workspace`, а в интерфейсе оставить русские названия как есть.
3. **Подтверждение стека.** Всё, что можно проверить без DAW и MIDI-клавиатуры,
   проверено (см. «Итоги прототипов этапа 0» ниже). Окончательно стек
   подтверждается после ручной проверки автором: перетаскивание в DAW,
   мост в четырёх DAW, клавиатура KeyLab.

## 2026-10-25 — Чем заменить Rust и Tauri

**Вопрос.** ТЗ рекомендовало Tauri 2 с движком на Rust. Автору Rust не подходит;
просьба автора — выбрать другой язык и фреймворк.

**Решение.** Предварительное: окончательно стек подтверждается по итогам
прототипов этапа 0.

| Часть | Язык | Чем сделана |
| --- | --- | --- |
| Интерфейс | TypeScript, HTML, CSS | WebView2 — движок веб-страниц, встроенный в Windows 10 и 11 |
| Оболочка (окна, перетаскивание файлов) | C# | .NET 10, WinForms и элемент WebView2 |
| Движок (MIDI, звук, файлы, связь с мостом) | C# | .NET 10, без привязки к Windows |
| Мост MiliPlain Bridge | C++ | CLAP SDK и clap-wrapper, который делает из CLAP-плагина VST3 |

**Почему.**

- Программа остаётся лёгкой. Как и Tauri, она рисует интерфейс через WebView2,
  который уже стоит в Windows, а не везёт свой Chromium, как Electron.
- C# читается проще, чем Rust и C++: строгие типы, понятные ошибки,
  память освобождается сама. Из быстрых языков он самый щадящий для новичка.
- Всё нужное уже установлено у автора: .NET 10 SDK и Visual Studio 2026.
- Для музыки на C# есть зрелые библиотеки под MIT: DryWetMIDI (MIDI-файлы
  и устройства), MeltySynth (синтезатор SoundFont), NAudio (вывод звука, WAV).
  Каждую запишем в журнал отдельной строкой, когда она действительно понадобится.
- Перетащить файл из окна в DAW в Windows можно одной стандартной функцией
  (OLE Drag&Drop). В WinForms это `DoDragDrop`.
- Перенос на macOS и Linux. Движок пишется на чистом .NET и работает везде.
  К Windows привязана только тонкая оболочка `app/shell`. Для другой системы
  пишется своя оболочка, например на Photino.NET (Apache-2.0), а движок
  и интерфейс не меняются.

**Почему мост на C++, а не на C#.** Плагин загружается внутрь чужой программы,
то есть DAW. Официальные SDK для VST3 и CLAP написаны на C и C++, а среда .NET
внутри DAW — лишний риск падений и конфликтов. Мост маленький: принять ноты,
отдать темп. Третий язык на такую задачу обходится дёшево.

**Что отвергнуто.**

- *Electron.* Один язык (TypeScript) на всё, но в каждой программе свой Chromium:
  больше памяти и места на диске, медленнее запуск. ТЗ отказалось от него
  по той же причине.
- *Go и Wails.* Простой язык, но нет готового перетаскивания файлов наружу,
  а для MIDI нужен cgo, то есть сборка C-кода.
- *Только C++ (с библиотекой webview).* Самый быстрый вариант, но самый трудный
  для новичка.
- *Tauri без своего кода на Rust.* Rust всё равно нужен для сборки и для MIDI.

**Лицензии основы** (проверены по файлам лицензий при сборке прототипов).
.NET и WinForms — MIT. WebView2 SDK (NuGet-пакет `Microsoft.Web.WebView2`) —
BSD-3-Clause. CLAP SDK и clap-wrapper — MIT. VST3 SDK 3.8 — MIT.
TypeScript — Apache-2.0, Vite — MIT.

**Следствие для ТЗ.** Папка `target/`, которую ТЗ просит внести в `.gitignore`,
не нужна: это папка сборки Rust. Вместо неё там `bin/` и `obj/` (так их называет
.NET) и `build/` (так их называет CMake для моста).

## 2026-10-25 — Где живёт модель проекта

**Вопрос.** Интерфейс написан на TypeScript, движок — на C#. В какой из частей
хранить проект: паттерны, ноты, историю отмены?

**Решение.** Предварительное, уточняется на этапе 1. Модель проекта и история
отмены живут в интерфейсе (TypeScript). Движок получает от интерфейса готовый
снимок паттерна, когда нужно его проиграть, сохранить или перетащить.

**Почему.** ТЗ требует одного способа хранить состояние, а не двух. Если хранить
модель в C#, интерфейсу пришлось бы держать её копию для отрисовки, и копий
стало бы две. Пианоролл при этом должен откликаться мгновенно на 5 000 нот,
поэтому данные лучше держать рядом с отрисовкой. Моды тоже пишутся
на TypeScript и работают с моделью напрямую. Движку остаётся то, где нужна
скорость и доступ к системе: MIDI-клавиатура, звук, мост, файлы.

## 2026-10-25 — Третья часть программы: app/shell

**Вопрос.** В черновике структуры (ТЗ, раздел 10) у `app/` две части: `ui`
и `engine`. Куда класть код, привязанный к Windows?

**Решение.** Частей три: `ui`, `engine` и `shell`.

**Почему.** В `shell` лежит всё, что зависит от Windows: окна, WebView2,

требование «никаких Windows-only решений в ядре без прослойки».

## 2026-10-25 — Как называются описания папок

**Вопрос.** Описание папки лежит в `GiDo/map/<имя_папки>.md`. Как быть, если
у двух папок одинаковые имена (например, `ui` будет и в программе,
и в подпрограммах)?

**Решение.** Имя файла — путь к папке через точку: `app/ui/` описывает
`app.ui.md`. Корень репозитория описывает `root.md`.

**Почему.** Путь не повторяется, а при сортировке описание вложенной папки
оказывается рядом с описанием родительской.

## 2026-10-25 — Пустые папки

**Вопрос.** Git не хранит пустые папки. Как сохранить утверждённую структуру,

## 2026-10-25 — Итоги прототипов этапа 0

**Вопрос.** Выдерживает ли выбранный стек четыре главных риска из ТЗ?

**Что сделано.** Четыре выбрасываемых прототипа:
пробное окно (C#, WinForms, WebView2) с пианороллом на 5000 нот, перетаскиванием
паттерна и MIDI-входом; мост (CLAP и VST3 из одного кода); маленький тестовый
CLAP-хост вместо DAW; имитация программы, которая шлёт мосту ноты.

**Результаты на компьютере разработки.** Видеокарта — дискретная, а не слабая
встроенная, поэтому замеры Canvas делались ещё и с искусственным замедлением
процессора в 4 и 6 раз.

| 3. Задержка «программа → мост → DAW» | от окна до моста — в среднем 0,1–0,25 мс (единичный выброс 5 мс); до выхода из моста в DAW — в среднем 3,6 мс, не больше 7 мс | своя задержка — меньше 1 мс; остальное — ожидание ближайшего звукового блока DAW (256 сэмплов при 48 кГц = 5,3 мс), то есть задержка самой системы |

**Решение.** Стек не меняется. Окончательно подтвердить его должна ручная
проверка автора (раздел «Ждут решения автора», пункт 3).

**Что надо учесть дальше.**
- Обзор «все ноты сразу» без видеокарты медленный. На этапе 2: при мелком

## 2026-10-25 — WebView2: не проверять репутацию своей страницы

**Вопрос.** Почему пробное окно открывалось 3 секунды, хотя страница лежит
рядом с exe?

**Решение.** Для окна программы выключается SmartScreen-проверка адресов
(`CoreWebView2Settings.IsReputationCheckingRequired = false`).

**Почему.** Замеры по этапам показали: 2 секунды WebView2 ждал перед загрузкой
страницы, пока SmartScreen по сети проверит репутацию адреса. Адрес наш,
выдуманный и локальный, проверять его незачем. Без проверки окно готово через
1,4 с вместо 3,1. Отключение прокси (`--no-proxy-server`) на время не повлияло
и не нужно.

## 2026-10-25 — Адрес страницы интерфейса: домен .example

**Вопрос.** Под каким адресом WebView2 показывает страницу из папки программы?

**Решение.** `https://miliplain.example/…`

**Почему.** Домен `.example` зарезервирован и никогда не существует в интернете.
Домен `.local` занят под поиск устройств в локальной сети (mDNS), а настоящий
домен мог бы перехватить чужой сайт.

## 2026-10-25 — Мост отдаёт ноты событиями CLAP, а не сырым MIDI

**Вопрос.** В каком виде мост передаёт ноты в DAW?

**Решение.** Событиями `CLAP_EVENT_NOTE_ON` и `CLAP_EVENT_NOTE_OFF` с номером
канала.

**Почему.** VST3-версию моста собирает clap-wrapper, а он переводит в VST3
только эти события. Сырые MIDI-события (`CLAP_EVENT_MIDI`) он на выходе молча
отбрасывает. Это проверено по его исходному коду и тестовым хостом.

**Следствие для этапа 5.** Контроллеры и pitch bend таким способом наружу
не пройдут. Понадобится доработка clap-wrapper (отдать её авторам) или
VST3-часть моста, написанная напрямую на VST3 SDK.

## 2026-10-25 — Версия VST3 SDK для моста

**Вопрос.** Какую версию VST3 SDK брать?

**Решение.** Ту, на которой закреплён clap-wrapper: сейчас `v3.8.0_build_66`.

**Почему.** Новейшая 3.8.1 с clap-wrapper 0.17.0 не компилируется. Обе версии
под MIT. Обновляемся вместе с clap-wrapper, а не раньше.

## 2026-10-25 — Мост вшивает в себя среду выполнения C++

**Вопрос.** Что делать, если на компьютере пользователя нет Visual C++
Redistributable?

**Решение.** Мост собирается со статической средой выполнения
(`CMAKE_MSVC_RUNTIME_LIBRARY = MultiThreaded`), без внешних DLL.

**Почему.** Иначе DAW просто не загрузит плагин и не скажет почему. Плагин
от этого становится больше на несколько сотен килобайт: обе версии моста
вместе весят около 1 МБ.

## 2026-10-25 — Связь программы и моста: UDP внутри компьютера

**Вопрос.** Как программа и мост в DAW обмениваются нотами и транспортом?

**Решение.** Предварительное, окончательный протокол — на этапе 5. Короткие
UDP-пакеты на адресе 127.0.0.1. Программа слушает порт 47800. Каждый мост
занимает свободный порт и раз в секунду сообщает программе, что он жив.

**Почему.** UDP прост и одинаково работает в Windows, macOS и Linux. Внутри
одного компьютера пакеты не теряются и доходят за доли миллисекунды (замер —
0,1–0,25 мс). Брандмауэр не вмешивается, потому что наружу ничего не уходит.
Звуковой поток DAW с сетью не работает: между ним и сетевым потоком моста
стоят очереди без блокировок, иначе в звуке появятся щелчки.

## 2026-10-25 — Чем рисовать пианоролл

**Вопрос.** Canvas 2D или WebGL (ТЗ, п. 5.2)?

**Решение.** Canvas 2D.

**Почему.** В рабочем масштабе он держит 5000 нот с запасом даже при
замедлении процессора в 6 раз (см. «Итоги прототипов этапа 0»). Видимые ноты
рисуются по 16 цветовым группам, каждая группа — одним вызовом. Слабое место —
обзор всех нот сразу без видеокарты, оно решается на этапе 2 упрощённой
отрисовкой. WebGL понадобится, только если этого не хватит на слабом
компьютере автора.

# Этап 1. Ядро проекта

## 2026-10-25 — Модель неизменяемая, история — список прошлых версий

**Вопрос.** Как устроить историю отмены, чтобы она покрывала все действия
пользователя (ТЗ, п. 6.9) и не ломалась?

**Решение.** Объекты модели (проект, канал, паттерн, нота) неизменяемые.
Каждая правка возвращает новую версию проекта, старая остаётся как была.
История хранит прошлые версии целиком. Отмена возвращает предыдущую версию,
повтор — следующую.

**Почему.** Обычный способ — для каждого действия писать «как его откатить».
Это много кода, а ошибка в откате незаметно портит проект. Список версий
откатывает любое действие, даже то, которое появится через год, и ошибиться
в нём нельзя. Копия дешёвая: соседние версии делят всё, что не менялось
(при правке одной ноты из 5000 копируется только список нот одного паттерна).
Заодно бесплатно получаются ещё две вещи. «Изменилось ли что-то» — это
сравнение ссылок (`===`). «Есть ли несохранённое» — сравнение текущей версии
с сохранённой, и после отмены до сохранённого состояния отметка исчезает сама.

Правка, которая ничего не меняет, возвращает тот же объект и в историю
не попадает. Лимит по умолчанию — 100 шагов, допустимо от 1 до 10 000.

## 2026-10-25 — Одно хранилище, выбор вне истории

**Вопрос.** Где хранить, какой паттерн открыт и в какой канал пишутся ноты?

**Решение.** В том же хранилище (`ProjectStore`), что и проект, но не
в истории отмены. Правка может сразу выбрать новый объект (`store.edit(…,
{ patternId })`): правка и выбор применяются вместе, подписчики узнают об этом
один раз. Если выбранный паттерн или канал исчез, выбирается первый.

**Почему.** ТЗ требует одного способа хранить состояние. Выбор — не правка
проекта: в FL Studio переключение паттерна не отменяется через Ctrl+Z.
Одно оповещение на правку с выбором — урок LARD: смена паттерна в две
ступени давала мигание.

## 2026-10-25 — Жесты: много правок — один шаг истории

**Вопрос.** Перетаскивание ноты — это сотни мелких правок. Как сделать из них
один шаг отмены?

**Решение.** `beginGesture` → правки → `endGesture`. Правки внутри жеста
сразу видны на экране, но в историю пишется один шаг. `cancelGesture`
(например, по Esc) возвращает всё как было до жеста.

**Почему.** Иначе Ctrl+Z после перетаскивания отменял бы его по одному пикселю.

## 2026-10-25 — Минимум один канал и один паттерн

**Вопрос.** Что будет, если удалить последний канал или паттерн, и что
делать с нотами удалённого канала?

**Решение.** Последний канал и последний паттерн не удаляются. Удаление
канала удаляет его ноты во всех паттернах.

**Почему.** Новой ноте всегда нужен канал, а пианороллу — открытый паттерн.
Ноты без инструмента играть некому, так же поступает FL Studio. Удаление
отменяется одним Ctrl+Z вместе с нотами.

## 2026-10-25 — Время в тиках, 960 на четверть; номера — UUID

**Вопрос.** В чём хранить время нот и как нумеровать объекты?

**Решение.** Время — целые тики, 960 на четверть: самое частое значение
в DAW, точнее любой сетки квантизации. Число записывается в файл, чтобы его
можно было поменять в будущем. Номера объектов — UUID (`crypto.randomUUID`).

**Почему.** Целые тики не накапливают ошибок округления, как дробные доли.
UUID уникален без общего счётчика — это пригодится, когда ноты будут
вставляться из другого проекта или из мода.

## 2026-10-25 — Настройки проекта появятся вместе с функциями

**Вопрос.** ТЗ (п. 6.1) упоминает «настройки проекта». Какие поля завести сейчас?

**Решение.** Пока никаких, кроме темпа, размера и разрешения. Поля добавятся
вместе с функциями, которым они нужны (например, лад и гамма — этап 6),
через новую версию формата и миграцию.

**Почему.** Поля «на будущее» без функции нечем проверить, и они почти
всегда оказываются не такими, как нужно. Формат версионирован, так что
добавить поле позже ничего не стоит.

## 2026-10-25 — Формат project.json и строгая проверка

**Вопрос.** Как устроен project.json и что делать с испорченным файлом?

**Решение.** В файле есть метка `"format": "miliplain-project"`, номер версии
формата и версия программы, которая его сохранила. При открытии проверяется
каждое поле: тип, границы, существование канала у каждой ноты, уникальность
номеров. Если что-то не так, проект не открывается. Пользователь видит до 20
ошибок с местом в файле, например
`project.patterns[0].notes[12].key: нужно целое число от 0 до 127`.
Неизвестные поля отбрасываются.

**Почему.** Тихо «починенный» проект опаснее неоткрывшегося: пользователь
не узнает, что часть нот пропала. Файл .mpj — обычный архив, его можно
поправить руками, поэтому сообщения называют точное место. Текущий проект
при неудачном открытии не трогается.

## 2026-10-25 — Миграции формата

**Вопрос.** Как новые версии программы будут открывать старые файлы
(ТЗ, п. 6.8)?

**Решение.** Для каждой старой версии формата есть функция перехода
к следующей. Файл версии 1 в программе с форматом 3 проходит переходы
1→2 и 2→3. Файл новее программы не открывается, а пользователь видит просьбу
обновить программу. Старые переходы никогда не удаляются и не меняются.
Порядок действий при смене формата записан в начале `formatVersions.ts`.

**Почему.** Цепочка маленьких переходов проще одного большого «из любой
версии в любую», и каждый переход проверяется отдельным тестом. Пока формат
один, механизм проверен на учебных переходах в тестах.

## 2026-10-25 — Файл .mpj: встроенный ZIP .NET и надёжная запись

**Вопрос.** Чем собирать ZIP и как не потерять проект при сбое записи?

**Решение.** ZIP пишет встроенный в .NET `System.IO.Compression`, без
сторонних библиотек. Запись надёжная: архив пишется во временный файл рядом
и одним действием подменяет старый (`AtomicFile`). Внутри архива пока только
`project.json`. Вложения (этап 4 и далее) лягут рядом отдельными файлами,
старые версии программы их не заметят. Движок не разбирает project.json —
он только кладёт текст в архив и достаёт обратно.

**Почему.** Встроенного ZIP хватает, лишняя зависимость не нужна. Если запись
прервётся (кончилось место, выключили свет), обрезанный архив иначе заменил бы
рабочий проект. Формат проекта принадлежит одному месту — интерфейсу.
Будь его проверка ещё и в движке, при изменениях две копии разошлись бы.

## 2026-10-25 — Автосохранение

**Вопрос.** Где хранить резервные копии, сколько и когда их писать?

**Решение.**
- Папка: `%APPDATA%\MiliPlain\autosave\<номер проекта>\`, в ней копии с
  временем записи в имени и `info.json` с именем проекта.
- Копия пишется по таймеру (по умолчанию раз в 5 минут, настраивается
  от 1 до 120; 0 — выключено) и **только если проект изменился** с прошлой
  копии или сохранения.
- Хранится 5 последних копий на проект (настраивается от 1 до 50). Папки
  проектов, к которым месяц не прикасались, удаляются при запуске.
- Восстановленная копия открывается как новый несохранённый проект:
  «Сохранить» спросит, куда, и не затрёт исходный файл.

**Почему.** Номер проекта, а не имя файла: копии есть и у ещё не
сохранённого проекта, и они не теряются при переименовании. Одинаковые
копии вытеснили бы полезные — поэтому пишем только изменения. Номер проекта
становится именем папки, поэтому в нём разрешены лишь буквы, цифры и дефис:
иначе «номер» вроде `..\..\Windows` вывел бы запись за пределы папки.

## 2026-10-25 — Настройки программы хранит движок

**Вопрос.** Где хранить настройки (глубина отмены, автосохранение)?

**Решение.** В `%APPDATA%\MiliPlain\settings.json`. Читает, пишет и проверяет
границы движок (`SettingsStore`). Испорченный файл или отсутствующее поле
заменяются значениями по умолчанию, запуск не срывается.

**Почему.** Интерфейс не имеет доступа к диску. Проверка границ в одном месте,
у владельца файла, — интерфейс получает уже исправленные значения.

## 2026-10-25 — Журнал работы

**Вопрос.** Как вести журнал (ТЗ, п. 6.9: только локально, с ротацией)?

**Решение.** `%APPDATA%\MiliPlain\logs\miliplain-ГГГГ-ММ-ДД.log`: файл
на день, хранятся 10 последних. Ошибка записи журнала не роняет программу.
Необработанные ошибки пишутся в журнал и показываются пользователю, а не
закрывают окно молча.

**Почему.** Файл на день проще всего найти, когда пользователь пишет «вчера
сломалось». Десяти дней хватает, чтобы разобраться, и журнал не разрастается.

## 2026-10-25 — Как интерфейс разговаривает с оболочкой

**Вопрос.** Как TypeScript-интерфейс просит C#-оболочку открыть файл или
показать диалог?

**Решение.** JSON-сообщения через WebView2. Просьба
`{kind: "request", id, method, params}` → ответ
`{kind: "response", id, ok, result | error}`. Оболочка может сама прислать
событие `{kind: "event", name, payload}`. Весь список методов собран
в `hostApi.ts` (интерфейс) и `HostMethods.cs` (оболочка), имена совпадают.
Закрытие окна с несохранённым: оболочка не закрывается, а присылает событие
`closeRequested`. Интерфейс задаёт вопрос «Сохранить изменения?», сохраняет
или отказывается и сам просит закрыть окно.

**Почему.** Один формат на все просьбы — один разборщик (`MessageRouter`)
вместо десятка обработчиков. Ошибка оболочки (диск переполнен) приходит
ответом с текстом и показывается пользователю, а не роняет интерфейс.
Вопрос о сохранении задаёт интерфейс, потому что только он знает проект.

## 2026-10-25 — Экран этапа 1 без библиотек

**Вопрос.** Брать ли сейчас библиотеку интерфейса (React, Svelte, Solid)?

**Решение.** Нет. Экран этапа 1 — простые функции, которые строят DOM
(`view/dom.ts`), и полная перерисовка панелей при изменении. Библиотеку
выберем на этапах 2–3, когда станет понятно, что нужно пианороллу и панелям.

*Дополнение этапа 2:* пианоролл — холст, ему библиотека не нужна. Панели
перерисовываются только при изменении того, что они показывают. Вопрос
о библиотеке остаётся до этапа 3 (список паттернов, стойка каналов).

**Почему.** Экран этапа 1 временный и маленький, его задача — дать потрогать
модель, отмену и сохранение. Выбирать библиотеку для интерфейса, которого
ещё нет, — гадание.

## 2026-10-25 — Временное до этапа 7

**Решение.** Надписи интерфейса собраны в одном файле `app/strings.ts`,
горячие клавиши вписаны в `app/hotkeys.ts`. На этапе 7 надписи переедут
в языковые пресеты, а клавиши станут переназначаемыми командами.

**Почему.** Так их потом не придётся искать по всему коду. Модификатор
горячих клавиш — `ctrlKey` (урок LARD: на Windows проверять Ctrl, а не только
Cmd).

## 2026-10-25 — Версия программы — в одном месте

**Решение.** Версия задана в `app/Directory.Build.props` (`0.0.10a`).
Оболочка сообщает её интерфейсу, интерфейс пишет её в project.json.

**Почему.** Когда версия записана в нескольких местах, они обязательно
разойдутся.

## 2026-10-25 — Vite 7, а не Vite 8: копилефт в зависимостях

**Вопрос.** Проверка лицензий всех установленных npm-пакетов показала, что
Vite 8 обязательно тянет за собой `lightningcss` (сжатие CSS) под лицензией
**MPL-2.0**. Это «слабый копилефт», а правило 0.5 запрещает любой копилефт.

**Решение.** Vite 7.3.7. В нём `lightningcss` — необязательное дополнение,
и оно не ставится. Vitest 5 работает с Vite 7.

**Почему.** Правило не делает исключений для инструментов сборки, а Vite 7
даёт всё, что нужно. После замены все 115 npm-пакетов под разрешёнными
лицензиями: MIT — 80, Apache-2.0 — 22, MIT или Apache-2.0 — 11, ISC — 1,
BSD-3-Clause — 1. Если автор решит, что инструмент, который не попадает
в программу, может быть под MPL-2.0, можно перейти на Vite 8, заменив одну
строку в `package.json`.

**Как проверять дальше.** Лицензии надо смотреть после каждого добавления
пакета: копилефт может прийти не с самим пакетом, а с его зависимостью.
Сбор лицензий скриптом — этап 10.

**Попутно.** npm 11 по умолчанию не запускает установочные скрипты пакетов
и предупреждает об `esbuild`. Ничего одобрять не нужно: esbuild находит свою
программу в отдельном пакете `@esbuild/win32-x64`, сборка и тесты работают.

## 2026-10-25 — Порт отладки в режиме разработки

**Вопрос.** Как подключать отладчик и автотесты к интерфейсу внутри окна?

**Решение.** С параметром `--ui-dev` оболочка открывает у WebView2 порт
отладки 9222. В обычном запуске порта нет, нет и инструментов разработчика
(F12) и стандартного меню страницы.

**Почему.** К этому порту подключается отладчик VS Code («Attach to Microsoft
Edge») с точками остановки прямо в TypeScript, и через него же Playwright
проверял окно вживую. Пользователю порт не нужен, и держать его открытым
в обычной программе незачем.

## 2026-10-25 — Скрипты PowerShell в UTF-8 с BOM

**Вопрос.** Почему `scripts/*.ps1` сохранены с BOM, хотя остальные файлы — без?

**Решение.** Только скрипты PowerShell сохраняются в UTF-8 с BOM.

**Почему.** Встроенный в Windows 10 PowerShell 5.1 читает файл без BOM
в старой кодировке. Русские комментарии превращаются в мусор, и скрипт
не запускается (проверено). Остальные инструменты (Node, .NET, Git) BOM
не нужен.

# Этап 2. Пианоролл LARD

## 2026-10-26 — Пианоролл правит ноты одного канала

**Вопрос.** Паттерн хранит ноты нескольких каналов (ТЗ, п. 6.1). Какие ноты
видит и правит пианоролл?

**Решение.** Только ноты выбранного канала в открытом паттерне, как в FL Studio.
Новые ноты пишутся в выбранный канал, выделить можно только его ноты.

**Почему.** ТЗ отдельно называет ghost-ноты других каналов (п. 6.2, этап 6):
это возможно, только если пианоролл показывает один канал, а остальные —
«призраками». Если бы пианоролл правил все каналы сразу, при щелчке было бы
непонятно, в какой канал ставить ноту.

## 2026-10-26 — Выделение нот и настройки редактора — в том же хранилище

**Вопрос.** Где хранить выделенные ноты, текущий инструмент и привязку?

**Решение.** В `ProjectStore`, рядом с выбором паттерна и канала, но вне
истории отмены. Правка может сразу выделить ноты (`store.edit(…, { noteIds })`):
вставленные или продублированные ноты выделяются в той же транзакции.
Удалённые ноты сами выпадают из выделения.

**Почему.** Один способ хранить состояние (ТЗ, п. 5.2). Выделение нужно не только
пианороллу: командам копирования, позже — редактору velocity (этап 6) и модам.
В историю выделение не пишется, как и в FL Studio: Ctrl+Z отменяет правки,
а не щелчки мышью.

## 2026-10-26 — Инструменты и жесты

**Вопрос.** Как устроить четыре инструмента так, чтобы их можно было проверить
тестами и расширить на этапе 6?

**Решение.** Инструмент решает только одно: что начать по нажатию мыши.
Начатое действие — «жест» — живёт до отпускания кнопки и получает движения
мыши. Жесты общие: поставить и тянуть, перетащить, растянуть, рамка,
стирание, кисть. Каждый жест, меняющий проект, — один шаг истории.
Логика не знает про холст: ей нужны только окно просмотра (перевод пикселей
в тики и высоты) и хранилище, поэтому тесты гоняют инструменты без экрана.

**Как ведут себя инструменты.** Как в FL Studio:
- Draw (P) — метод LARD: левая кнопка ставит ноту в клетку сетки и сразу тянет её;
- Paint (B) — протяжка рисует ряд нот;
- Delete (D) — стирает;
- Select (E) — рамка и выделение.

Во всех инструментах правая кнопка стирает, а зажатая — стирает протяжкой
(путь проверяется с шагом 2 пикселя, чтобы быстрый росчерк не перепрыгивал
ноты). Ctrl + протяжка — рамка выделения. Alt временно отключает привязку.
Новая нота берёт длину последней тронутой ноты.

**Почему.** Так новый инструмент этапа 6 (Mute, Slice, Zoom) — это ещё один
маленький объект, а не правка большого обработчика мыши.

## 2026-10-26 — Привязка и квантизация

**Вопрос.** Какие варианты привязки и как работает квантизация?

**Решение.** Привязка: такт, доля, 1/2, 1/3 (триоли), 1/4 («шаг» FL Studio,
по умолчанию), 1/6, 1/8 доли или без привязки. Доля зависит от знаменателя
размера. При перетаскивании к сетке прижимается начало ноты, за которую
взялись, остальные выделенные сохраняют расстояние до неё. Квантизация
(Ctrl+Q) прижимает начала нот к ближайшей линии сетки и не трогает
длительность, как «быстрая квантизация» FL Studio. Без выделения
квантизуются все ноты канала.

**Почему.** Группа должна двигаться как целое: если прижимать каждую ноту
отдельно, аккорд с «живой» игрой разваливался бы. Групповой сдвиг
упирается в начало паттерна и края клавиатуры целиком, аккорд не сплющивается.

## 2026-10-26 — Команды и горячие клавиши: три слоя уже сейчас

**Вопрос.** ТЗ (п. 7) требует переназначаемых клавиш через три слоя, но это
этап 7. Делать ли слои сейчас, раз клавиш стало много?

**Решение.** Да. Команды с именами (`app/commands.ts`), таблица «команда —
сочетание» с раскладкой по умолчанию как в FL Studio (`app/keymap.ts`)
и диспетчер (`app/hotkeys.ts`). На этапе 7 останется загружать таблицу
из пресетов и сделать окно переназначения.

Клавиша определяется по месту на клавиатуре (`event.code`), а не по букве
(`event.key`). В поле ввода работают только команды файла.

**Почему.** Иначе горячие клавиши этапа 2 пришлось бы переписывать на этапе 7.
По букве в русской раскладке P пришла бы как «з», и инструменты переключались
бы только в английской (проверено вживую). Delete и стрелки в поле ввода
должны править текст, а не ноты.

## 2026-10-26 — Копирование и вставка нот

**Вопрос.** Куда вставлять скопированные ноты?

**Решение.** На те же места по времени, откуда скопированы, в выбранный канал,
как в FL Studio. Вставленные ноты выделяются, их сразу можно перетащить.
Ctrl+B дублирует выделение сразу справа от него, сдвиг округляется вверх
до шага сетки. Буфер обмена — внутри программы, у каждой вставки новые номера нот.

**Почему.** Так копирование между паттернами сохраняет ритмическое положение.
Системный буфер обмена (между двумя окнами MiliPlain) отложен: на этапе 2
он не нужен.

## 2026-10-26 — Пианоролл и показатели раздела 4

**Вопрос.** Укладывается ли пианоролл в цели ТЗ (п. 4)?

**Как мерили.** Настоящее окно MiliPlain, 5000 нот (кнопка «Тест: 5000 нот»),
замер скорости из инструментов разработчика. Видеокарта здесь дискретная,
поэтому процессор дополнительно замедлялся в 4 и 6 раз, чтобы изобразить
слабый ноутбук. Время отрисовки одного кадра, среднее:

| Режим | Без замедления | ×4 | ×6 |
| --- | --- | --- | --- |
| Прокрутка в рабочем масштабе | 0,9 мс | 3,4 мс | 5,3 мс (81 кадр/с) |
| Обзор всех 5000 нот | 2,4 мс | 8,3 мс | 14 мс (55 кадров/с) |
| Перетаскивание одной ноты | 0,9 мс | 3,3 мс | 4,7 мс (75 кадров/с) |
| Перетаскивание 500 нот | 0,9 мс | 3,4 мс | 4,9 мс (65 кадров/с) |

| Показатель | Цель ТЗ | Результат |
| --- | --- | --- |
| Память в простое, проект на 5000 нот | до 300 МБ | 226 МБ (пустой проект — 193 МБ) |
| Запуск до готового окна | до 3 с | 1,2–1,3 с, первый запуск после сборки — 2,2 с |

**Решение.** Canvas 2D подтверждён, WebGL не нужен. Одна оптимизация сделана
по замерам: ноты складываются в пути по цветам сразу, без промежуточного
объекта на каждую ноту. На ×6 обзор всех нот ускорился с 36 до 55 кадров/с,
а перетаскивание 500 нот — с 50 до 65.

**Что осталось проверить.** Настоящий слабый компьютер со встроенной графикой.
Это ручная проверка автора.

## 2026-10-26 — Временная кнопка «Тест: 5000 нот»

**Решение.** В строке инструментов пианоролла есть кнопка «Тест: 5000 нот»
(штриховая рамка). Она добавляет 5000 случайных нот в выбранный канал.
Кнопка временная и уберётся, когда появится импорт MIDI (этап 3): тогда
большой проект можно будет просто открыть.

**Почему.** Иначе автору нечем проверить руками показатель «плавно при 5000 нот».

## 2026-10-26 — Инструменты замера только в режиме разработки

**Решение.** `window.miliplainDev` (добавить ноты, замер скорости, состояние
пианоролла для автотестов) подключается только в режиме разработки
(`import.meta.env.DEV`). Vite выбрасывает этот код из собранной программы
(проверено поиском по сборке).

**Почему.** Пользователю он не нужен, а живые автотесты и замеры без него
проверяли бы только картинку.
